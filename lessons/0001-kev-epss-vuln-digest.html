用 KEV × EPSS 做出你自己的漏洞简报

你要做安全资讯 —— 第一个真本事不是「会看新闻」，而是「能自己判优先级」。

这一课结束时，你手上会有一份自己跑出来的漏洞简报，并且能对其中任何一条说清楚： 为什么它排在前面、证据在哪、以及它对你到底算不算事。

为什么不能只有一个分数

绝大多数人刚开始读漏洞情报时，只看一个数字：CVSS。它回答的是 「这个漏洞本身有多严重」，而排优先级要回答的是 「它有多可能打到我」。这是两个问题，需要三个不同来源的指标一起看。

CVSS
Common Vulnerability Scoring System · FIRST · 当前规范 v4.0

漏洞自身的技术严重度，0–10 分。它与是否已被利用无关：CVSS 9.8 却从没人打过的高危漏洞一直都有。

EPSS
Exploit Prediction Scoring System · FIRST · 模型说明

未来 30 天内该漏洞被利用的概率（0–1），外加一个分位。注意它是概率，不是严重度。

KEV
Known Exploited Vulnerabilities · CISA 目录

已经被观察到在野利用的漏洞清单，每条都带修复期限。攻击链已经真实跑通，这是最硬的信号。

一个反直觉的实测结果

把 KEV 目录和 EPSS 评分表拉下来对齐（命令见文末），会看到这样一组数字：

  • 近 30 天新加入 KEV 的条目，EPSS 中位数是 0.022；
  • 更早进入 KEV 的存量条目，EPSS 中位数是 0.510。

刚被确认「正在被真实利用」的漏洞，概率反而低一个数量级。结论： EPSS 跟随已观测到的利用活动，不是预测未来的先知。 所以「EPSS 高 = 紧急」是错的读法，正确用法是拿它给有资产的漏洞排先后。

踩坑记录

这个项目第一版是按总分把所有条目全局排序的，结果首页被 2008–2012 年的老漏洞占满； 改用「EPSS ≥ 0.5 就算 P0」后，1739 条里 867 条（49.9%）都进了最高档 —— 一半清单变红，等于没排。 信号本身没问题，是用法错了：KEV 是累积清单，日报的主体必须是增量。

动手：产出并读懂你的简报

  1. 跑起来。首次运行会下载 KEV 目录（约 1.7 MB）与 EPSS 评分表（约 2.6 MB），之后走缓存。

    npm run digest

    产物：out/YYYY-MM-DD.md（人读）、out/YYYY-MM-DD.json（程序用）、out/feed.xml（RSS）。

  2. 只读 P0 那一段。打开 Markdown，先看「近 30 天新增且满足勒索/高概率」的条目 —— 这才是今天值得你花时间的部分。

  3. 交叉验证一条。挑一条 P0，去 CISA 官方目录搜同一个 CVE，核对 dateAdded、dueDate、勒索标注三项是否与本地一致。

    这一步是安全资讯可信度的根：你的数据管道可能只是缓存旧了，也可能是解析错了 —— 只有跟上游对账才知道。

  4. 跟官方 API 对一次 EPSS。

    curl -s "https://api.first.org/data/v1/epss?cve=CVE-2015-3306"

    比对本地简报里的 EPSS 数值：差异通常来自评分日期（EPSS 每天更新一次），而不是你的代码写错了。

  5. 给自己出一道难题。从 P2 里挑一条，写下「我要不要修它」以及判断依据。你会发现情报本身答不了这个问题 —— 缺的是资产上下文：这台机器上到底装没装。

完成检查

  • 我能说清 CVSS / EPSS / KEV 各自回答什么问题
  • 我能解释为什么「EPSS 高就等于严重」是错的
  • 我交叉验证过至少一条 P0 与官方目录一致
  • 我说出了一个只有资产测绘才能回答、情报答不了的问题

检索练习

凭记忆答，别回头翻。点完立刻有反馈。

1. CISA KEV 目录直接回答的问题是？

严重度是 CVSS 的活，概率是 EPSS 的活。KEV 只回答「有没有已经在被真实利用」，因此它不需要再论证攻击可行性，是优先级里最硬的一票。

2. EPSS 分数很高，最准确的解读是？

EPSS 是概率：「未来 30 天内被利用的可能性」。是否「已经被利用」是 KEV（或其他利用证据）回答的问题；两者可能不一致，本课实测的 EPSS 滞后现象就是一例。

3. 新加入 KEV 的条目 EPSS 中位数只有 0.022，存量却是 0.510。最合理的解释是？

KEV 的门槛就是「已观察到真实利用」，所以第三条自相矛盾；严重度与 EPSS 是两套指标，第二条也不成立。剩下唯一的解释：EPSS 的输入里包含已发生的利用活动，因此对刚被确认利用的漏洞反应滞后。

4. 要把 KEV 变成每天能看的简报，第一步应该做什么？

KEV 是累积清单（当前 1739 条），全量排序只会把十年前的老漏洞顶上来；而 867 条超过 0.5 概率，全修不现实。日报的主体是增量：最近新增了什么，其余作为存量备查。

接下来

  • 让它自动跑：加一条 cron / GitHub Actions 定时任务，把 out/feed.xml 或 Markdown 推到邮箱、企业微信或 Telegram。这一步就叫「你有安全资讯能力了」。
  • 做成产品：把 digest.json 包一层 HTTP API（Node 原生 http 就够），加 /v1/kev?since=7d&tier=P0 这类查询参数，就是一个可被别人调用的小服务。
  • 做成课程：本课踩的两个坑（全量排序、概率当严重度）就是最好的教学案例 —— 你已经在讲「为什么」，而不是「是什么」。
  • 补上缺的那一半：情报解决「会被打吗」，资产测绘解决「打得到我吗」。这是 ROADMAP 里的项目 2。
