漏洞优先级

把「多严重」「会不会被利用」「已经发生了吗」三件事分开，是排优先级的第一步。

四个指标各回答一个问题

指标回答的问题取值一手来源别拿它当优先级
CVE ID 这是哪一个漏洞 编号，本身不含严重度 CVE Program 把它当评分
CVSS 漏洞自身的技术严重度 0–10（v4.0 为当前规范） FIRST CVSS · v4.0 规范 它与是否被利用无关；CVSS 9.8 无人利用的漏洞一大把
EPSS 未来 30 天内被利用的概率 0–1（外加分位） FIRST EPSS · 模型说明 它是概率不是严重度，也不是「先知」：见下方实测
KEV 是否已被观察到在野利用 在列 / 不在列，附修复期限 CISA KEV 目录 它是累积清单，整张当待办会淹死人
资产上下文 我到底有没有这个资产 有 / 没有 / 暴露与否 自建资产测绘（见 ROADMAP 项目 2） ——
SSVC 该做哪个动作 Act / Attend / Track* / Track CISA SSVC ——

决策顺序

  1. 在 KEV 里吗？在 = 已经被真实利用过，攻击链已验证。这是最硬的信号，不需要再论证。
  2. 我有这个资产吗？没有就归档，别修。这一步只有资产测绘能回答，情报本身永远答不了。
  3. EPSS 多少？有资产时用它排先后：概率高的先修。
  4. 交给 SSVC 定动作：暴露面、可自动化利用程度、技术影响共同决定是「立刻」还是「关注」。

常见误用

  • 按 CVSS 排序：得到的是「理论上最惨的漏洞」，不是「最可能被打的漏洞」。
  • 把 EPSS 高当严重：EPSS 是概率。0.9 的漏洞可能只是 Apache 组件众多、扫描器满天飞。
  • KEV 全量当待办：1700+ 条里绝大多数与你无关；不做资产匹配，清单就是噪音。
  • 用「逾期」分档：CISA 给的修复期限对历史条目早已全部过期（实测 1739/1739），区分度为 0。
  • 把排序分当风险分：排序分只用于「先看哪条」，不含业务影响，也不能替代 SSVC。

命令备忘

npm run digest                    # 生成 out/YYYY-MM-DD.md · .json · feed.xml
node tools/kev-digest/digest.mjs --refresh        # 忽略缓存重新拉取
node tools/kev-digest/digest.mjs --days 7         # 只看近 7 天新增
node tools/kev-digest/digest.mjs --limit 20       # 控制台多打印几条
